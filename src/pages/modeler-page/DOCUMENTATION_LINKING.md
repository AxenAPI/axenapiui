### **Функционал связи элементов графа и страниц документации в AxenAPI**

Связь между элементами графа (например, сервисы, топики, события) и страницами документации является ключевым функционалом AxenAPI. Этот механизм позволяет пользователям легко переходить от технических компонентов системы к соответствующей документации и наоборот, обеспечивая целостность информации и удобство работы. Ниже описан подробный функционал этого механизма.

---

### **1. Основная идея**

Элементы графа (сервисы, топики, события и т.д.) могут быть связаны с одной или несколькими страницами документации. Это позволяет:

- Предоставлять контекстную информацию для каждого элемента.
- Объединять технические и бизнесовые аспекты системы.
- Упрощать навигацию между API и документацией.

---

### **2. Создание связей**

#### **(a) Привязка страницы к элементу графа**

- **Где это делается**:
  - В информационной панели выбранного элемента графа (правая панель).
- **Как это работает**:
  - Пользователь открывает элемент графа (например, сервис `OrderService`).
  - В разделе "Linked Documentation" пользователь выбирает существующую страницу документации из выпадающего списка или создает новую.
- **Пример интерфейса**:
  - Кнопка "Add Documentation" добавляет новую связь.
  - Выпадающий список показывает доступные страницы документации.

#### **(b) Привязка нескольких страниц**

- **Как это работает**:
  - Пользователь может связать один элемент графа с несколькими страницами документации.
  - Например, сервис `PaymentService` может быть связан с:
    - "Technical Details".
    - "Business Logic".
    - "Integration Guide".
- **Ограничения**:
  - Рекомендуется группировать страницы по категориям (например, "Technical", "Business") для улучшения навигации.

---

### **3. Навигация между элементами графа и документацией**

#### **(a) Из графа к документации**

- **Как это работает**:
  - Пользователь кликает на элемент графа (например, сервис `OrderService`).
  - В информационной панели отображается список связанных страниц документации.
  - Клик на название страницы открывает её в редакторе или в режиме просмотра.
- **Пример интерфейса**:
  - Раздел "Linked Documentation" содержит ссылки:
    - "Order Processing Workflow".
    - "Order Service API".

#### **(b) Из документации к графу**

- **Как это работает**:
  - На каждой странице документации есть раздел "Linked Elements".
  - В этом разделе отображаются все элементы графа, связанные с текущей страницей.
  - Клик на элемент открывает его в графе.
- **Пример интерфейса**:
  - Страница "Order Processing Workflow" связана с:
    - Сервисом `OrderService`.
    - Топиком `OrderTopic`.

---

### **4. Управление связями**

#### **(a) Добавление связей**

- **Как это работает**:
  - Пользователь может добавить новую связь через информационную панель элемента графа или через саму страницу документации.
  - При добавлении связи система проверяет её уникальность (например, одна и та же страница не может быть дважды связана с одним элементом).

#### **(b) Удаление связей**

- **Как это работает**:
  - Пользователь может удалить связь через информационную панель элемента графа или через страницу документации.
  - Удаление связи не удаляет саму страницу документации.

#### **(c) Редактирование связей**

- **Как это работает**:
  - Пользователь может изменить связь (например, заменить одну страницу на другую).
  - Все изменения сохраняются автоматически или после подтверждения.

---

### **5. Особенности реализации**

#### **(a) Использование уникальных идентификаторов**

- **Зачем это нужно**:
  - Для предотвращения поломки ссылок при перемещении или переименовании страниц.
- **Как это работает**:
  - Каждая страница документации имеет уникальный идентификатор (UUID).
  - Связи используют этот идентификатор, а не имя страницы.

#### **(b) Автоматическое обновление ссылок**

- **Как это работает**:
  - Если страница переименована или перемещена, все связанные элементы графа автоматически обновляют ссылки.
  - Это гарантирует целостность данных.

---

### **6. Преимущества функционала**

#### **(a) Целостность информации**

- Все связанные материалы остаются доступными в одном месте, что уменьшает риск потери важных данных.

#### **(b) Удобство навигации**

- Пользователи могут быстро находить нужную информацию, не теряя контекста.

#### **(c) Гибкость**

- Возможность связывать один элемент графа с несколькими страницами документации позволяет охватить разные аспекты описания.

#### **(d) Совместная работа**

- Команды могут одновременно работать над документацией и элементами графа, используя Git для управления версиями.

---

### **7. Пример использования**

#### **Сценарий:**

1. **Создание связей**:
   - Пользователь создает новый сервис `PaymentService`.
   - Для этого сервиса создаются три страницы документации:
     - "Payment Service API".
     - "Payment Processing Workflow".
     - "How to Integrate Payment Service".
   - Пользователь связывает все три страницы с сервисом через информационную панель.

2. **Навигация**:
   - Разработчик кликает на `PaymentService` в графе.
   - В информационной панели видит список связанных страниц:
     - "Payment Service API".
     - "Payment Processing Workflow".
     - "How to Integrate Payment Service".
   - Переходит к нужной странице.

3. **Работа с документацией**:
   - На странице "Payment Service API" пользователь видит раздел "Linked Elements":
     - Сервис `PaymentService`.
     - Топик `PaymentTopic`.
   - Переходит к элементам графа через этот раздел.

---

### **8. Заключение**

Функционал связи элементов графа и страниц документации в AxenAPI обеспечивает удобство работы с распределенными системами. Благодаря этому механизму пользователи могут легко находить и использовать всю необходимую информацию, будь то техническое описание, бизнес-логика или инструкции по интеграции. Реализация этого функционала делает платформу более универсальной и эффективной для управления проектами.

### **Можно ли связывать элемент графа сразу с несколькими страницами документации?**

Да, в AxenAPI можно и даже рекомендуется реализовать возможность связывания одного элемента графа (например, сервиса, топика или события) с несколькими страницами документации. Это может быть полезно в следующих случаях:

---

### **1. Обоснование необходимости**

- **Разные аспекты описания**:
  - Один элемент графа может требовать описания с разных точек зрения. Например:
    - Техническая документация (описание API, JSON Schema).
    - Бизнес-логика (описание бизнес-процессов, связанных с элементом).
    - Инструкции для разработчиков (гайды по интеграции, примеры использования).
- **Удобство навигации**:
  - Пользователи смогут быстро переходить к нужному разделу документации, не теряя контекста.

---

### **2. Реализация функционала**

#### **(a) Привязка нескольких страниц**

- **Как это работает**:
  - В информационной панели элемента графа (например, сервиса) добавляется раздел "Linked Documentation".
  - Пользователь может выбрать несколько страниц документации из выпадающего списка или дерева.
  - Каждая связанная страница отображается как отдельная ссылка.

- **Пример интерфейса**:
  - Сервис `OrderService` связан с:
    - "Technical Details" (техническое описание).
    - "Business Logic" (бизнес-процессы).
    - "Integration Guide" (инструкция по интеграции).

#### **(b) Двунаправленная навигация**

- **Из графа в документацию**:
  - Пользователь кликает на элемент графа и видит список связанных страниц.
  - Переход к любой из страниц осуществляется через соответствующую ссылку.
- **Из документации в граф**:
  - На каждой странице документации есть раздел "Linked Elements", где указаны связанные элементы графа.

---

### **3. Преимущества такого подхода**

#### **(a) Гибкость**

- Разные страницы документации могут охватывать различные аспекты одного элемента, что делает систему более универсальной.

#### **(b) Удобство**

- Пользователи могут легко находить нужную информацию без необходимости просматривать всю документацию.

#### **(c) Целостность**

- Все связанные материалы остаются доступными в одном месте, что уменьшает риск потери важных данных.

---

### **4. Возможные ограничения**

- **Сложность управления**:
  - Если элемент связан с большим количеством страниц, это может усложнить навигацию. Рекомендуется ограничивать количество связей или группировать их по категориям (например, "Technical", "Business", "Guides").
- **Поддержка целостности**:
  - При удалении или переименовании страницы необходимо автоматически обновлять связи, чтобы избежать "битых" ссылок.

---

### **5. Пример использования**

#### **Сценарий:**

1. Пользователь создает новый сервис `PaymentService`.
2. Для этого сервиса создаются три страницы документации:
   - "Payment Service API" (техническое описание).
   - "Payment Processing Workflow" (бизнес-логика).
   - "How to Integrate Payment Service" (инструкция для разработчиков).
3. В информационной панели `PaymentService` пользователь связывает все три страницы.
4. При работе с графом пользователь видит список связанных страниц:
   - "Payment Service API".
   - "Payment Processing Workflow".
   - "How to Integrate Payment Service".
5. Пользователь выбирает нужную страницу и переходит к ней.

## **3. Хранение связей в `_index.json`**

Все связи хранятся в поле **`linked_objects`** файла `_index.json` страницы:

```json
{
  "id": "doc-7a3b9f1c-e2d1-4abc-8f1a-0123456789ab",
  "title": "API OrderService",
  "linked_objects": [
    {
      "type": "service",
      "id": "svc-order-service"
    },
    {
      "type": "http_node",
      "id": "http-post-orders"
    },
    {
      "type": "topic",
      "id": "tpc-order-created"
    }
  ],
  "child_pages": [
    {
      "id": "doc-a1b2c3d4-e5f6-7890-g1h2-i3j4k5l6m7n8",
      "title": "API",
      "order": 1,
      "has_children": true
    }
  ]
}
```

### **Структура `linked_objects`**

Каждая связь представляет собой объект с полями:

- **`type`**: тип объекта (`service`, `http_node`, `topic`, `event`)
- **`id`**: уникальный ID объекта в системе

> ⚠️ **Важно**: Связи хранятся **только по ID**, а не по имени или пути. Это гарантирует их устойчивость при переименовании или перемещении объектов.

## **5. Обработка удаленных объектов**

### **Сценарий: объект моделера удален, но ссылка в документации осталась**

#### **Как система определяет проблему**

При загрузке страницы:

1. AxenAPI проверяет существование каждого объекта из `linked_objects`
2. Если объект не найден (например, удален сервис), система помечает связь как **"битая"** и предлагает заменить

#### **Визуальное отображение**

- В разделе "Связанные объекты":
  - Объект отображается **полупрозрачным**
  - Добавляется иконка предупреждения ⚠️
  - Текст: _"Объект не найден (ID: svc-old-service)"_
  - Подсказка при наведении: _"Этот объект был удален. Обновите документацию или удалите связь."_

#### **Действия пользователя**

1. **Игнорировать** (если объект действительно устарел)
2. **Заменить** на новый объект (кнопка "Заменить")
3. **Удалить** связь (кнопка "Удалить")

> 💡 Система **не блокирует удаление объектов** из-за связей в документации, так как:
>
> - Это создало бы циклические зависимости
> - Удаление объекта может быть частью рефакторинга
> - Документация должна адаптироваться к изменениям архитектуры

---

## **6. Обработка удаленных страниц документации**

### **Сценарий: страница документации удалена, но объект моделера ссылается на нее**

#### **Как система определяет проблему**

- При загрузке графа архитектуры:
  - AxenAPI проверяет все ссылки на документацию
  - Если страница не найдена, связь помечается как нерабочая

#### **Визуальное отображение в графе**

- У объекта:
  - Иконка документа становится **серой**
  - При наведении: _"Связанная документация не найдена"_

#### **Автоматические действия системы**

- В фоновом режиме создается запись в **журнале проблем**
- При экспорте документации — предупреждение в отчете

#### **Ручные действия**

- Архитектор может:
  - Создать новую страницу документации
  - Привязать существующую страницу
  - Удалить метаданные о связи через API

---

## **7. Рекомендации по работе с "битыми" связями**

### **Для аналитиков и технических писателей**

- Регулярно проверяйте раздел **"Проблемы связей"** в панели управления
- Используйте фильтр **"С устаревшими связями"** при работе с документацией
- При рефакторинге архитектуры — обновляйте документацию в том же MR

### **Для архитекторов**

- При удалении объекта оставляйте **переадресацию**:
  ```json
  {
    "id": "svc-old-service",
    "redirect_to": "svc-new-service"
  }
  ```
- Используйте метку **"deprecated"** для объектов перед удалением

### **Для разработчиков**

- Внедрите проверку связей в **CI/CD pipeline**:
  ```bash
  axenapi check-links --branch=main
  ```
- Настройте **уведомления** в Slack при обнаружении битых связей

1. список связанных страницы - множество UUID
