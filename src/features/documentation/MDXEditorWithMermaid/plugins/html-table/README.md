# HTML Table Plugin - Архитектура и Принципы Дизайна

## Обзор

Плагин HTML Table обеспечивает поддержку сырых HTML таблиц в MDXEditor. В отличие от GFM (GitHub Flavored Markdown) таблиц, которые используют синтаксис с вертикальными чертами, HTML таблицы сохраняют сложное форматирование, встроенные стили и HTML структуру.

**Ключевая цель дизайна**: Отображение HTML таблиц из существующего контента с сохранением безопасности и целостности данных.

## Основные обязанности

### 1. Распознавание HTML таблиц

Плагин должен:

- Обнаруживать элементы `<table>` в markdown исходнике
- Различать HTML таблицы и GFM pipe таблицы
- Обрабатывать таблицы с различными структурами (с/без thead, tbody, tfoot)
- Обрабатывать таблицы, встроенные в другой markdown контент

Плагин НЕ должен:

- Автоматически конвертировать GFM таблицы в HTML таблицы
- Модифицировать поведение существующего GFM table плагина
- Перехватывать не-табличные HTML элементы

### 2. Безопасность и санитизация

**Критическое требование безопасности**: Все HTML таблицы ДОЛЖНЫ быть санитизированы перед рендерингом.

Плагин должен:

- Удалять ВСЕ потенциально опасные HTML атрибуты (onclick, onload, onerror, и т.д.)
- Удалять теги `<script>` и ссылки с протоколом javascript:
- Блокировать URI с протоколом data:
- Сохранять только безопасные HTML теги и атрибуты
- Применять санитизацию в КАЖДОЙ точке, где обрабатывается HTML:
  - При импорте markdown (конвертация MDAST → Lexical)
  - При обновлении содержимого ячеек
  - При манипуляции строками/столбцами
  - При экспорте (конвертация Lexical → MDAST)

Плагин НЕ должен:

- Доверять любому пользовательскому HTML без санитизации
- Разрешать выполнение inline обработчиков событий
- Разрешать произвольные HTML теги внутри ячеек таблицы
- Пропускать санитизацию для "внутренних" операций

**Whitelist подход**: Разрешены только явно указанные теги и атрибуты. Всё остальное удаляется.

### 3. Нормализация структуры таблицы

Плагин должен:

- Всегда обеспечивать наличие `<thead>` с заголовочной строкой
- Всегда обеспечивать наличие `<tbody>` с хотя бы одной строкой данных
- Заполнять отсутствующие ячейки пустыми ячейками для поддержания прямоугольной структуры
- Сохранять консистентность количества столбцов во всех строках
- Обрабатывать некорректный HTML gracefully без падений

Плагин НЕ должен:

- Создавать таблицы с несогласованным количеством столбцов в строках
- Разрешать таблицы без заголовков (даже если в исходном HTML нет thead)
- Сохранять невалидные структуры таблиц, которые сломают редактирование

### 4. Сохранение данных

Плагин должен:

- Сохранять текстовый контент точно как предоставлено (после санитизации)
- Поддерживать настройки выравнивания столбцов (left, center, right, justify)
- Поддерживать inline форматирование внутри ячеек (жирный, курсив, код, ссылки)
- Обеспечивать round-trip таблиц без потери данных: Import → Edit → Export → Import

Плагин НЕ должен:

- Удалять валидные теги inline форматирования (strong, em, code, a)
- Терять информацию о выравнивании при трансформациях
- Изменять текстовый контент кроме как по соображениям безопасности

### 5. Возможности редактирования

**Текущая фаза**: Read-only отображение с программными методами редактирования.

Плагин должен предоставлять:

- Обновление содержимого ячеек через MDAST phrasing content
- Вставку строк в любую позицию
- Удаление строк с очисткой таблицы
- Вставку столбцов в любую позицию
- Удаление столбцов
- Изменение выравнивания столбцов
- Запросы количества строк/столбцов
- Управление фокусом для будущей интеграции UI

Плагин НЕ должен:

- Предоставлять API для прямой манипуляции DOM
- Разрешать редактирование в обход методов мутации ноды
- Пропускать санитизацию при программном редактировании

### 6. Интеграция с редактором

Плагин должен:

- Мирно сосуществовать с GFM table плагином
- Использовать паттерн DecoratorNode для рендеринга
- Генерировать правильные события фокуса для будущей интеграции редактора
- Поддерживать клавиатурную навигацию
- Работать как в Rich text режиме, так и в Source режиме

Плагин НЕ должен:

- Вмешиваться в редактирование GFM таблиц
- Блокировать или переопределять стандартное поведение Lexical
- Требовать модификаций глобального состояния редактора

## Архитектура потока данных

### Конвейер импорта (Markdown → Редактор)

1. **Парсинг MDAST**: Micromark парсит HTML в markdown в MDAST html ноды
2. **Обнаружение таблицы**: MdastImportVisitor идентифицирует элементы `<table>` внутри html нод
3. **Извлечение HTML**: Извлечение outerHTML элемента таблицы
4. **Санитизация** (КРИТИЧНО): Санитизация HTML перед созданием Lexical ноды
5. **Создание ноды**: Создание HtmlRawTableNode с санитизированным HTML
6. **Рендеринг**: DecoratorNode рендерит таблицу в read-only viewer компоненте

**Контрольная точка безопасности**: Шаг 4 - санитизация ДОЛЖНА происходить здесь.

### Конвейер экспорта (Редактор → Markdown)

1. **Обход нод**: LexicalExportVisitor встречает HtmlRawTableNode
2. **Извлечение HTML**: Получение HTML контента из ноды
3. **Повторная санитизация** (КРИТИЧНО): Санитизация снова как defense-in-depth
4. **Конвертация MDAST**: Конвертация в MDAST html ноду с санитизированной таблицей
5. **Сериализация**: Mdast-to-markdown выводит HTML таблицу в markdown

**Контрольная точка безопасности**: Шаг 3 - санитизация перед экспортом, даже если уже санитизировано.

### Конвейер редактирования (Действие пользователя → Обновление ноды)

1. **Взаимодействие пользователя**: Будущий UI инициирует редактирование (например, клик по ячейке, кнопка добавления строки)
2. **Вызов метода ноды**: Вызов соответствующего метода мутации на HtmlRawTableNode
3. **Парсинг текущего HTML**: Конвертация HTML строки в структурированные данные таблицы
4. **Применение мутации**: Модификация структуры таблицы (добавление/удаление/обновление ячеек)
5. **Сериализация обратно**: Конвертация структурированных данных обратно в HTML строку
6. **Санитизация** (КРИТИЧНО): Санитизация нового HTML
7. **Обновление ноды**: Обновление внутреннего HTML контента ноды
8. **Повторный рендеринг**: Lexical инициирует повторный рендеринг с новым HTML

**Контрольная точка безопасности**: Шаг 6 - каждая мутация проходит через санитизацию.

## Представление структуры

Плагин поддерживает HTML таблицы в ТРЁХ представлениях:

### 1. HTML строка (Формат хранения)

- Как хранится в Lexical ноде
- Что экспортируется в markdown
- Сырой HTML как строка с правильными тегами и атрибутами

### 2. Структурированные данные таблицы (Формат редактирования)

- Промежуточный формат для манипуляции
- Содержит:
  - Массив выравниваний столбцов
  - Заголовочная строка с ячейками
  - Массив строк тела с ячейками
  - Каждая ячейка имеет: тип (th/td), выравнивание, MDAST контент
- Используется при операциях редактирования

### 3. MDAST Phrasing Content (Формат содержимого ячейки)

- Как представлено содержимое ячейки
- Поддерживает: text, emphasis, strong, inlineCode, link, break, html
- Позволяет rich форматирование внутри ячеек
- Должно быть конвертируемо в/из HTML

**Поток трансформации**: HTML строка ↔ Структурированные данные ↔ MDAST контент

## Обработка выравнивания

### Выравнивание на уровне столбца

Плагин должен:

- Поддерживать четыре типа выравнивания: left, center, right, justify
- Хранить выравнивание на уровне столбца (применяется ко всем ячейкам в столбце)
- Отображать в HTML атрибут align на элементах th/td
- По умолчанию использовать 'left' для новых столбцов
- Сохранять выравнивание через все трансформации

Плагин НЕ должен:

- Поддерживать переопределение выравнивания на уровне ячейки (только выравнивание столбца)
- Смешивать CSS text-align с атрибутом align (использовать атрибут align)
- Изменять выравнивание при добавлении/удалении строк
- Терять выравнивание при изменении порядка столбцов

### Выравнивание в разных контекстах

- **Импорт**: Извлечение атрибутов align из элементов th/td
- **Экспорт**: Применение атрибутов align к элементам th/td
- **Редактирование**: Поддержка массива выравниваний столбцов независимо от данных ячеек
- **Новый контент**: Использование выравнивания столбца для новых ячеек

## Поддержка inline форматирования

### Разрешённые inline элементы

Плагин должен поддерживать внутри содержимого ячеек:

- Обычный текст
- Жирный (`<strong>`, `<b>`)
- Курсив (`<em>`, `<i>`)
- Код (`<code>`)
- Ссылки (`<a href="...">`)
- Переносы строк (`<br>`)

Плагин НЕ должен поддерживать:

- Блочные элементы внутри ячеек (div, p, и т.д.)
- Изображения в начальной версии (будущее улучшение)
- Вложенные таблицы
- Элементы форм (input, select, и т.д.)
- Кастомные HTML элементы

### Парсинг контента

При парсинге innerHTML ячейки:

- Сохранять текстовые ноды
- Конвертировать теги жирный/курсив в MDAST emphasis/strong
- Конвертировать `<code>` в MDAST inlineCode
- Конвертировать `<a>` в MDAST link (санитизировать href!)
- Удалять неподдерживаемые теги, но сохранять текстовый контент

## Обработка ошибок

### Невалидный HTML

Плагин должен:

- Парсить HTML gracefully используя DOMParser
- Обрабатывать отсутствующие элементы таблицы (thead, tbody)
- Автоматически создавать заголовочную строку если отсутствует
- Заполнять неполные строки пустыми ячейками
- Возвращать пустую структуру при ошибке парсинга

Плагин НЕ должен:

- Генерировать исключения, которые крушат редактор
- Повреждать существующий контент при встрече с плохим HTML
- Молча удалять контент без осведомлённости пользователя

### Некорректная структура

При встрече с:

- **Нет заголовочной строки**: Создать одну с пустыми ячейками
- **Несогласованное количество столбцов**: Нормализовать до максимального количества столбцов
- **Отсутствует tbody**: Создать из прямых потомков tr
- **Пустая таблица**: Разрешить (может быть заполнена через редактирование)

### Нарушения безопасности

Когда санитизация обнаруживает опасный контент:

- Удалить опасные атрибуты/теги
- Сохранить безопасный контент
- Продолжить обработку (не падать на всей таблице)
- Никогда не выполнять любой пользовательский код

## Соображения производительности

Плагин должен:

- Парсить HTML только когда необходимо (ленивый парсинг)
- Кешировать распарсенную структуру во время операций мутации
- Избегать ненужных DOM операций
- Повторно сериализовать только при изменении контента

Плагин НЕ должен:

- Парсить HTML при каждом рендеринге
- Создавать избыточные DOM ноды
- Блокировать главный поток большими таблицами
- Создавать утечки памяти от event listeners

## Требования к тестированию

Все операции с таблицами должны быть протестированы на:

1. **Безопасность**: XSS векторы заблокированы
2. **Структура**: Таблицы остаются валидными после операций
3. **Round-trip**: Import → Export → Import сохраняет данные
4. **Граничные случаи**: Пустые таблицы, одна ячейка, большие таблицы
5. **Санитизация**: Применяется во всех точках мутации

### Что предоставляет плагин

- Класс HtmlRawTableNode для Lexical
- Import visitor для конвертации MDAST → Lexical
- Export visitor для конвертации Lexical → MDAST
- Утилиты санитизации
- Утилиты парсинга/сериализации таблиц
- Функция htmlTablePlugin() для MDXEditor

### Что ожидает плагин

- Экземпляр Lexical редактора
- Micromark с включённой поддержкой HTML
- MDAST с типом ноды html
- React для рендеринга
- DOMPurify для санитизации

### Что другие плагины НЕ должны делать

- Модифицировать экземпляры HtmlRawTableNode напрямую
- Обходить санитизацию
- Конвертировать HTML таблицы в GFM таблицы без действия пользователя
- Перехватывать HTML элементы связанные с таблицами

## Краткое изложение принципов дизайна

1. **Безопасность прежде всего**: Каждая HTML операция проходит через санитизацию
2. **Целостность структуры**: Таблицы всегда валидны и прямоугольны
3. **Сохранение данных**: Контент переживает round-trips без изменений
4. **Graceful degradation**: Невалидный HTML нормализуется, а не отвергается
5. **Разделение ответственности**: Отображение, редактирование и хранение - отдельные слои
6. **Эшелонированная защита**: Множественные контрольные точки санитизации
7. **Явное важнее неявного**: Whitelist подход для всего HTML
8. **Безопасный отказ**: Ошибки не должны крушить редактор или выполнять код

## Принципы архитектуры компонентов

### Separation of Concerns (Разделение ответственностей)

**Проблема "божественного компонента":** Когда один компонент делает слишком много - управляет состоянием, обрабатывает события, содержит бизнес-логику, рендерит UI - код становится:

- Трудным для понимания (500+ строк в одном файле)
- Сложным для тестирования (нельзя протестировать части отдельно)
- Хрупким при изменениях (изменение одной части ломает другую)
- Невозможным для повторного использования

**Решение через Custom Hooks:** Вынести каждую ответственность в отдельный custom hook:

1. **useActiveCellWithBoundaries** - управление выбором ячейки
   - Ответственность: валидация координат, обработка границ
   - Вход: данные таблицы, parent editor, table node
   - Выход: activeCell state, setActiveCellWithBoundaries функция
   - Логика: overflow/underflow координат, создание новых параграфов
   - НЕ отвечает за: рендеринг, события мыши, сохранение данных

2. **useTableHighlight** - управление подсветкой при hover
   - Ответственность: отслеживание координат под курсором
   - Вход: нет внешних зависимостей
   - Выход: highlightedCoordinates state, onMouseOver, onMouseLeave
   - Логика: поиск ячейки в DOM, вычисление индексов
   - НЕ отвечает за: активацию ячеек, навигацию, редактирование

3. **useTableOperations** - операции манипуляции таблицей
   - Ответственность: добавление строк/столбцов, обновление ноды
   - Вход: parent editor, table node, callback для фокуса
   - Выход: addRowToBottom, addColumnToRight функции
   - Логика: вызов методов ноды, управление фокусом
   - НЕ отвечает за: рендеринг UI, валидацию, парсинг

**Преимущества этого подхода:**

- Каждый hook можно протестировать независимо
- Переиспользование в других компонентах (например, в будущих вариантах таблицы)
- Понятная ответственность - название hook говорит что он делает
- Легко найти где живёт определённая логика
- Изменения в одном hook не влияют на другие

**Как применять:**

- Если логика занимает >20 строк и имеет чёткую цель - вынести в hook
- Если state используется только для одной цели - вынести в hook
- Если несколько функций работают с одним state - объединить в hook
- Если логика может понадобиться в другом месте - обязательно hook

**Как НЕ применять:**

- НЕ создавать hook для одной строки кода
- НЕ дублировать всю логику в hook если она используется в одном месте
- НЕ смешивать несвязанные ответственности в одном hook
- НЕ делать hook зависимым от деталей реализации компонента

### Type Safety (Безопасность типов)

**Проблема `any` типов:**

- Компилятор не ловит ошибки
- IDE не даёт автокомплит
- Рефакторинг становится опасным
- Легко передать неправильный тип

**Решение - строгие типы:**

```typescript
// ❌ ПЛОХО
const cache = new WeakMap<any, string>()
const getCellKey = (cell: any) => { ... }

// ✅ ХОРОШО
const cache = new WeakMap<HtmlTableCell, string>()
const getCellKey = (cell: HtmlTableCell): string => { ... }
```

**Правила:**

- Каждая функция имеет явные типы параметров и возврата
- Используйте конкретные типы вместо any
- Создавайте интерфейсы для сложных структур
- Экспортируйте типы если они используются в других модулях

### Memory Management (Управление памятью)

**Проблема утечек памяти:**

- WeakMap в useMemo с пустыми зависимостями
- Event listeners без cleanup
- Ссылки на DOM элементы после unmount

**Решения:**

1. **useRef вместо useMemo для объектов:**

```typescript
// ❌ ПЛОХО - создаёт новый WeakMap при каждом ре-рендере
const getCellKey = useMemo(() => {
  const cache = new WeakMap()
  return (cell) => { ... }
}, []) // пустые зависимости!

// ✅ ХОРОШО - один WeakMap на весь lifecycle
const cellKeyCache = useRef(new WeakMap<HtmlTableCell, string>())
const getCellKey = useCallback((cell) => {
  const cache = cellKeyCache.current
  // ...
}, [])
```

2. **Cleanup в useEffect:**

```typescript
// ✅ ХОРОШО
useEffect(() => {
  const unsubscribe = lexicalTable.focusEmitter.subscribe(callback);
  return () => unsubscribe(); // cleanup!
}, [lexicalTable, callback]);
```

3. **WeakMap для ключей связанных с объектами:**

- Используйте WeakMap когда ключи - объекты
- Garbage collector автоматически очистит записи
- НЕ используйте Map для объектов-ключей (утечка!)

### Constants (Именованные константы)

**Проблема магических чисел:**

```typescript
// ❌ ПЛОХО - что значит -1? что значит 5?
const [coords, setCoords] = useState<[number, number]>([-1, -1])
<PopoverContent sideOffset={5}>
if (rowIndex === 0) { ... }
```

**Решение - именованные константы:**

```typescript
// ✅ ХОРОШО - понятно что это начальное значение
const INITIAL_COORDINATES: [number, number] = [-1, -1]
const [coords, setCoords] = useState(INITIAL_COORDINATES)

// ✅ ХОРОШО - понятно что это отступ для popover
const POPOVER_SIDE_OFFSET = 5
<PopoverContent sideOffset={POPOVER_SIDE_OFFSET}>

// ✅ ХОРОШО - понятно что это индекс заголовка
const HEADER_ROW_INDEX = 0
if (rowIndex === HEADER_ROW_INDEX) { ... }
```

**Правила:**

- Число используется >1 раза → константа
- Число имеет смысл (не просто 1, 2, 3) → константа
- Число может измениться в будущем → константа
- Называйте ЗАГЛАВНЫМИ_БУКВАМИ с подчёркиваниями

### Error Handling (Обработка ошибок)

**Принцип Graceful Degradation:**

- Невалидные данные → нормализуются
- Ошибки парсинга → возвращается пустая структура
- Отсутствующие элементы → создаются автоматически
- НЕ бросайте исключения которые крушат UI

**Валидация с предупреждениями:**

```typescript
// ✅ ХОРОШО - логируем проблему, но не падаем
if (colIndex < 0 || colIndex >= colCount) {
  console.warn(`Invalid cell coordinates: [${colIndex}, ${rowIndex}]`);
  return; // просто выходим
}
```

**Где должны быть throw Error:**

- В методах ноды когда индексы вне границ
- При попытке создать невалидную структуру
- В утилитах когда входные данные некорректны
- НО ловите эти ошибки на уровне UI!

**Как должно работать редактирование ячеек:**

#### Активация редактирования

- Клик по ячейке активирует режим редактирования
- Ячейка получает визуальный индикатор активности (data-active атрибут)
- Внутри ячейки создаётся вложенный Lexical редактор
- Курсор автоматически позиционируется в ячейке

#### Редактирование контента

- Ячейка ведёт себя как полноценный Lexical редактор
- Поддерживается inline форматирование (bold, italic, code, links)
- История изменений (undo/redo) работает на уровне ячейки
- Текст переносится автоматически внутри ячейки

#### Навигация между ячейками

- **Tab**: переход к следующей ячейке вправо
- **Shift+Tab**: переход к предыдущей ячейке влево
- **Enter**: переход к ячейке ниже в том же столбце
- **Shift+Enter**: переход к ячейке выше в том же столбце
- При переполнении столбца (Tab в последней ячейке строки):
  - Переход на первую ячейку следующей строки
  - Если это последняя строка → выход из таблицы
- При недополнении столбца (Shift+Tab в первой ячейке):
  - Переход на последнюю ячейку предыдущей строки
  - Если это первая строка → выход из таблицы
- При выходе из таблицы вниз (Enter в последней строке):
  - Фокус переходит на следующий элемент после таблицы
  - Если следующего элемента нет, создаётся новый параграф
- При выходе из таблицы вверх (Shift+Enter в заголовке):
  - Фокус переходит на предыдущий элемент

#### Сохранение изменений

- Изменения сохраняются автоматически при потере фокуса (blur)
- При переходе к другой ячейке (Tab/Enter):
  1. Содержимое текущей ячейки экспортируется в MDAST
  2. MDAST контент передаётся в метод updateCellContents
  3. Контент санитизируется
  4. Таблица обновляется с новым содержимым
  5. Фокус перемещается в новую ячейку
- При клике за пределами таблицы:
  - Контент сохраняется
  - Активная ячейка сбрасывается в null
  - Таблица переходит в режим просмотра

#### ReadOnly режим

- В readOnly режиме ячейки не становятся активными при клике
- Тулбар с кнопками управления таблицей скрыт
- Пользователь может выделять и копировать текст
- Навигация клавиатурой недоступна
- Структура таблицы полностью идентична editable режиму

#### Координаты ячеек

- Система координат: [colIndex, rowIndex]
- colIndex: индекс столбца (0-based), 0 = первый столбец
- rowIndex: индекс строки (0-based), 0 = заголовочная строка (thead)
- rowIndex >= 1: строки тела таблицы (tbody)
- Координаты используются для:
  - Определения активной ячейки
  - Навигации между ячейками
  - Обновления содержимого через API

#### Вложенные редакторы

- Каждая ячейка содержит независимый Lexical редактор
- Редакторы создаются лениво только для активных ячеек
- Редактор ячейки получает те же плагины что и основной редактор
- ContentEditable ячейки использует тот же theme что и root редактор
- История (History) работает отдельно для каждой ячейки
- Nested editor children (плагины) также применяются к ячейкам

#### Интеграция с родительским редактором

- Ячейка сообщает родительскому редактору об изменениях через NESTED_EDITOR_UPDATED_COMMAND
- При сохранении ячейки родительский редактор получает дискретное обновление
- Фокус контролируется через isPartOftheEditorUI утилиту
- Blur игнорируется если фокус переходит на другой UI элемент редактора

**Как НЕ должно работать:**

#### Избегать множественного активного состояния

- Только одна ячейка может быть активной одновременно
- При активации новой ячейки предыдущая сохраняется и деактивируется
- Нет режима "множественного выделения ячеек"

#### Не обходить процесс сохранения

- Изменения не должны применяться напрямую к DOM
- Всегда использовать updateCellContents для обновления
- Не манипулировать innerHTML ячеек напрямую
- Все изменения идут через Lexical state

#### Не создавать конфликты навигации

- Tab в обычном тексте внутри ячейки НЕ должен добавлять табуляцию
- Enter в обычном тексте НЕ должен создавать новый параграф в ячейке
- Навигационные команды имеют CRITICAL приоритет

#### Не терять фокус неожиданно

- Blur должен проверять что фокус реально покинул редактор
- Клики на тулбар или другие UI элементы НЕ должны вызывать blur
- Навигация между ячейками НЕ должна проходить через blur-focus цикл

**Как должно работать редактирование структуры:**

#### Редактор столбцов (Column Editor)

- Каждая заголовочная ячейка (в thead) имеет триггер меню столбца
- Клик по триггеру открывает popover с опциями столбца
- Меню содержит:
  - 3 кнопки выравнивания: left, center, right
  - Кнопка "вставить столбец слева"
  - Кнопка "вставить столбец справа"
  - Кнопка "удалить столбец"
- При изменении выравнивания:
  - Обновляется выравнивание всех ячеек в столбце
  - Изменения сразу видны визуально
  - HTML атрибут align применяется к th/td элементам
- При вставке столбца:
  - Новый столбец добавляется в указанную позицию
  - Все строки получают новую пустую ячейку
  - Фокус перемещается на первую ячейку нового столбца
  - Выравнивание по умолчанию - left
- При удалении столбца:
  - Столбец удаляется из всех строк
  - Если это последний столбец - удаляется вся таблица
  - Данные в других столбцах сохраняются

#### Редактор строк (Row Editor)

- Каждая строка тела таблицы имеет триггер меню строки
- Клик по триггеру открывает popover с опциями строки
- Меню содержит:
  - Кнопка "вставить строку выше"
  - Кнопка "вставить строку ниже"
  - Кнопка "удалить строку"
- При вставке строки:
  - Новая строка добавляется в указанную позицию
  - Все ячейки новой строки пустые
  - Количество ячеек = количеству столбцов
  - Выравнивание наследуется от столбцов
  - Фокус перемещается на первую ячейку новой строки
- При удалении строки:
  - Строка удаляется из тела таблицы
  - Если это последняя строка тела - удаляется вся таблица
  - Заголовочная строка НЕ удаляется этой операцией

#### Кнопки быстрого добавления

- В конце таблицы (footer) есть кнопка "добавить строку"
- Справа от таблицы есть кнопка "добавить столбец"
- Кнопка добавления строки:
  - Добавляет строку в конец тела таблицы
  - Фокус перемещается на первую ячейку новой строки
  - Видна всегда (кроме readOnly режима)
- Кнопка добавления столбца:
  - Добавляет столбец в конец таблицы (справа)
  - Фокус перемещается на заголовочную ячейку нового столбца
  - Видна всегда (кроме readOnly режима)

#### Удаление таблицы целиком

- Меню столбца содержит кнопку удаления таблицы
- При клике пользователь подтверждает удаление
- Вся таблица удаляется как Lexical нода
- Фокус перемещается на соседний элемент
- Операция НЕ обратима через обычный undo

#### Подсветка при наведении (Hover Highlighting)

- При наведении мыши на ячейку:
  - Запоминаются координаты [colIndex, rowIndex]
  - Соответствующий триггер столбца подсвечивается
  - Соответствующий триггер строки подсвечивается
  - Визуальная обратная связь показывает какой столбец/строка будут затронуты
- При уходе мыши с таблицы:
  - Подсветка сбрасывается
  - Координаты возвращаются в начальное состояние [-1, -1]
- Подсветка НЕ влияет на фокус или активную ячейку
- Используется только для визуальной обратной связи

#### Edge Cases и граничные условия

**Удаление последней строки:**

- Если в таблице только одна строка тела (headerRow + 1 bodyRow)
- При удалении этой строки:
  - Вся таблица удаляется полностью
  - Не остаётся "пустая таблица" только с заголовком
  - Фокус перемещается к следующему элементу
  - Если следующего нет - создаётся новый параграф

**Удаление последнего столбца:**

- Если в таблице только один столбец
- При удалении этого столбца:
  - Вся таблица удаляется полностью
  - Не остаётся "таблицы без столбцов"
  - Логика идентична удалению последней строки

**Вставка в начало/конец:**

- Индексы вставки валидируются:
  - Для строк: от 0 до bodyRows.length (включительно)
  - Для столбцов: от 0 до columnCount (включительно)
- Вставка на позицию = длине массива означает "добавить в конец"
- Вставка на позицию 0 означает "добавить в начало"

**Обновление координат:**

- После вставки столбца слева - все правые столбцы сдвигаются
- После удаления столбца - координаты пересчитываются
- Активная ячейка может стать невалидной после удаления
- В этом случае activeCell сбрасывается в null

#### Интеграция с режимом редактирования ячеек

**Совместная работа:**

- Редактирование структуры и редактирование ячеек работают независимо
- Можно редактировать ячейку и затем добавить строку
- Можно удалить столбец пока другая ячейка активна
- При структурных изменениях:
  - Активная ячейка сохраняется если возможно
  - Если её координаты стали невалидны - деактивируется

**Приоритеты операций:**

- Навигация Tab/Enter имеет приоритет внутри ячейки
- Клик на меню столбца/строки НЕ вызывает blur активной ячейки
- Сохранение ячейки происходит перед структурными изменениями
- Popover меню НЕ крадёт фокус у редактора

**ReadOnly режим:**

- Все меню столбцов/строк скрыты
- Кнопки добавления строк/столбцов скрыты
- Подсветка при наведении всё ещё работает
- Структура таблицы идентична editable режиму

- Импорт/экспорт CSV/Excel
- Copy/paste регионов таблицы
- Множественное выделение ячеек

Каждая фаза строится на предыдущей, поддерживая обратную совместимость и гарантии безопасности.

## Детали реализации редактирования ячеек

### Архитектура компонентов

**HtmlTableEditor** - главный компонент таблицы:

- Отвечает за рендеринг структуры таблицы (colgroup, thead, tbody)
- Управляет состоянием активной ячейки через React state
- Обрабатывает навигацию с учётом границ таблицы
- Интегрируется с focusEmitter ноды для программного управления фокусом
- Скрывает инструментальные столбцы в readOnly режиме

**Cell** - обёртка для каждой ячейки:

- Определяет активное состояние ячейки
- Применяет CSS классы для выравнивания
- Обрабатывает клик для активации
- Рендерит правильный HTML элемент (th для заголовков, td для данных)
- Передаёт data-active атрибут для стилизации

**CellEditor** - редактор содержимого ячейки:

- Создаёт вложенный Lexical редактор один раз при монтировании
- Импортирует начальное содержимое из MDAST в Lexical
- Регистрирует команды для навигации (Tab, Enter)
- Обрабатывает blur для сохранения изменений
- Экспортирует содержимое обратно в MDAST при сохранении
- Устанавливает фокус при активации

### Управление состоянием

**activeCell state**:

- Тип: `[colIndex, rowIndex] | null`
- null означает что ни одна ячейка не активна
- Только одна ячейка активна в любой момент времени
- Обновляется при:
  - Клике по ячейке
  - Навигации Tab/Enter
  - Blur событии
  - Программной установке через focusEmitter

**setActiveCellWithBoundaries**:

- Проверяет границы таблицы перед установкой
- Обрабатывает overflow/underflow координат
- При выходе за границы:
  - Сбрасывает activeCell в null
  - Перемещает фокус редактора за пределы таблицы
  - Создаёт новый параграф если нужно

**focusEmitter паттерн**:

- HtmlRawTableNode содержит coordinatesEmitter
- Позволяет программно установить фокус на ячейке
- Используется для будущих UI кнопок управления таблицей
- Subscribe/publish паттерн для связи node ↔ компонент

### Команды и приоритеты

**KEY_TAB_COMMAND**:

- Приоритет: CRITICAL (блокирует стандартное поведение Tab)
- preventDefault() вызывается всегда
- Shift+Tab: движение влево, Tab: движение вправо
- Вызывает saveAndFocus с новыми координатами

**KEY_ENTER_COMMAND**:

- Приоритет: CRITICAL (блокирует создание параграфа)
- preventDefault() вызывается всегда
- Shift+Enter: движение вверх, Enter: движение вниз
- Вызывает saveAndFocus с новыми координатами

**BLUR_COMMAND**:

- Приоритет: EDITOR (стандартный приоритет)
- Проверяет relatedTarget через isPartOftheEditorUI
- Если фокус остаётся в редакторе → игнорировать
- Если фокус покидает редактор → сохранить и деактивировать

**FOCUS_COMMAND**:

- Приоритет: LOW (не блокирует другие обработчики)
- Устанавливает ячейку как активную
- return false чтобы не блокировать propagation

**NESTED_EDITOR_UPDATED_COMMAND**:

- Приоритет: EDITOR
- Сохраняет и деактивирует ячейку
- Используется для синхронизации с другими nested editors

### Процесс сохранения

**saveAndFocus функция**:

1. Читает текущий EditorState вложенного редактора
2. Экспортирует Lexical tree в MDAST через exportLexicalTreeToMdast
3. Извлекает phrasing content из первого параграфа
4. Вызывает parentEditor.update с discrete: true
5. Вызывает lexicalTable.updateCellContents(colIndex, rowIndex, content)
6. Отправляет NESTED_EDITOR_UPDATED_COMMAND родителю
7. Вызывает setActiveCell с новыми координатами или null

**discrete: true**:

- Помечает обновление как дискретное (не batch с другими)
- Обеспечивает немедленное применение изменений
- Не создаёт точку undo/redo в истории родителя

### Парсинг и нормализация

**parseHtmlTable**:

- Используется в useMemo с зависимостью от htmlContent
- Вызывается только при изменении HTML содержимого ноды
- Возвращает структурированные данные: columnAligns, headerRow, bodyRows
- Обрабатывает ошибки и возвращает пустую структуру
- Результат кешируется React

**getCellKey**:

- Использует WeakMap для стабильных ключей ячеек
- Генерирует UUID один раз на ячейку
- Предотвращает ненужные re-renders при редактировании
- Ключи привязаны к объектам ячеек, не индексам

### Стилизация и классы

**AlignToTailwindClassMap**:

- left → leftAlignedCell
- center → centeredCell
- right → rightAlignedCell
- justify → leftAlignedCell (fallback)
- Применяется к col элементам и td/th элементам

**data-active атрибут**:

- Добавляется к активной ячейке для CSS стилизации
- Используется вместо CSS классов для производительности
- Удаляется автоматически при деактивации

**toolCell и tableToolsColumn**:

- Скрываются в readOnly режиме
- Зарезервированы для будущих UI контролов
- Не участвуют в координатной системе ячеек

### Интеграция с core плагином

**Используемые cells**:

- readOnly$ - определяет режим работы
- importVisitors$ - для парсинга содержимого ячеек
- exportVisitors$ - для сериализации содержимого ячеек
- usedLexicalNodes$ - ноды для вложенных редакторов
- rootEditor$ - для проверки фокуса
- nestedEditorChildren$ - дополнительные плагины для ячеек
- jsxComponentDescriptors$, directiveDescriptors$, codeBlockEditorDescriptors$ - для поддержки сложного контента
- jsxIsAvailable$ - флаг доступности JSX

**Не используются**:

- iconComponentFor$ - не используем иконки в текущей фазе
- editorRootElementRef$ - не нужен для текущей реализации
- toolbar$ связанные cells - таблица работает независимо от тулбара

### Соображения производительности

**Ленивое создание редакторов**:

- Редактор ячейки создаётся только один раз через useState
- Повторное открытие той же ячейки использует существующий редактор
- При деактивации редактор НЕ уничтожается (остаётся в памяти)

**Минимальные re-renders**:

- Используем useMemo для parseHtmlTable
- Используем useCallback для всех обработчиков
- getCellKey стабилизирует ключи ячеек
- React.memo не используется намеренно (сложность > выгода)

**Оптимизация команд**:

- Команды регистрируются один раз через useEffect
- mergeRegister для эффективной очистки
- return cleanup функция вызывается автоматически

### Тестирование редактирования

**Unit тесты должны проверять**:

- Сохранение структуры после редактирования
- Корректный экспорт обновлённого контента
- Обработку пустых ячеек
- Сохранение атрибутов align
- Round-trip: import → edit → export → import

**Integration тесты будут проверять** (будущее):

- Клик активирует ячейку
- Tab навигация работает корректно
- Enter навигация работает корректно
- Автосохранение при blur
- Выход из таблицы в нужные места

**НЕ тестируем в данный момент**:

- Программное обновление ячеек через API (нет публичного API на MDXEditorMethods)
- Интерактивные сценарии (требуют userEvent)
- Focus management детали (сложно в JSDOM)
