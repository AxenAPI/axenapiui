# Руководство по участию в разработке Axenapi UI

Этот документ описывает основные принципы, соглашения и процессы, принятые в проекте. Следуйте этому руководству, чтобы сделать процесс разработки более эффективным и поддерживать высокое качество кодовой базы.

## 1. Общая архитектура

Приложение имеет гибридную архитектуру, состоящую из трех основных частей:

- **Локальный Java-сервер (`axenapi-web.jar`)**: Выполняет всю основную бизнес-логику — генерацию артефактов, операции с Git, обработку схем. Предоставляет стандартный HTTP API.

- **Основной процесс Electron (`electron/main/index.ts`)**: Это «мозг» десктопного приложения. Он отвечает за:
  - Создание окна приложения (`BrowserWindow`).
  - Запуск и остановку дочернего процесса Java-сервера.
  - Обработку IPC-запросов от рендер-процесса для доступа к нативным возможностям ОС (например, диалоги сохранения файлов).

- **Рендер-процесс Electron (Frontend)**: React-приложение, которое видит пользователь. Оно взаимодействует с Java-сервером через HTTP-запросы и с основным процессом Electron через безопасный `preload`-скрипт.

- **Связующее звено (`electron/preload/index.ts`)**: Этот скрипт служит безопасным мостом между фронтендом (Renderer) и основным процессом Electron. Он предоставляет фронтенду строго определенный набор функций (`window.electronAPI`) для вызова нативных операций, предотвращая прямой доступ к `node.js` API из соображений безопасности.

## 2. Архитектура и процесс разработки Frontend

### Структура проекта (FSD)

Проект построен на основе методологии **Feature-Sliced Design (FSD)**. Эта архитектура организует код по бизнес-доменам (слайсам), а не по техническим типам файлов. Код разделен на слои, каждый из которых имеет свою зону ответственности.

- **`src/app`** — Инициализация приложения (роутер, провайдеры тем и т.д.).
- **`src/pages`** — Страницы приложения. Каждая страница — это отдельный слой, который координирует и связывает виджеты и фичи / сущности.
- **`src/widgets`** — Независимые и переиспользуемые блоки интерфейса, состоящие из более мелких компонентов (фич и сущностей). Например, шапка сайта или панель навигации.
- **`src/features`** — Конкретная бизнес-логика, которая несет ценность для пользователя (например, кнопка удаления).
- **`src/entities`** — Бизнес-сущности, которые содержит в себе бизнес данные (например, `Repository` или таблица).
- **`src/shared`** — Переиспользуемый технический код, который не привязан к бизнес-логике проекта (например, UI-кит, конфигурация API, вспомогательные утилиты).

**Основное правило:** Слои могут взаимодействовать только в порядке `shared` -> (`entities` / `features`) -> `widgets` / `pages` -> `app`. Код из нижних слоев ничего не должен знать о верхних.

### Работа с состоянием (Effector)

Вся бизнес-логика, управление состоянием и обработка сайд-эффектов должны быть инкапсулированы в моделях Effector. Это центральный принцип архитектуры проекта.

- **Stores (`$name`)**: Хранят состояние.
- **Events**: Описывают события, которые могут происходить в системе.
- **Effects**: Используются для асинхронных операций (например, API-запросов).

Логика должна быть максимально декларативной. Используйте `sample` для описания реакций и связей между юнитами.

### Структура компонента (слайса)

Каждый компонент (будь то `feature` или `entity`) следует четкой структуре для разделения ответственности:

```
feature/MyFeature/
├── ui/              # "Глупые" UI-компоненты — только отображение и события
├── model/           # Effector-логика (stores, events, effects, sample)
├── types/           # TypeScript типы и интерфейсы
│   └── types.ts     # Пропсы компонентов и другие типы слайса
└── hooks/           # Связь UI с моделью (useUnit)
```

- **`ui/`**: Директория для "глупых" UI-компонентов. Их задача — отображать данные и вызывать события, полученные из хуков. Они не должны содержать бизнес-логику. **Вспомогательные компоненты должны быть вынесены в отдельные файлы** внутри `ui/` (требование лида проекта) для улучшения читаемости и поддерживаемости кода.
- **`model/`**: Директория для Effector-модели. Здесь объявляются `stores`, `events` и `effects`, а также описываются все сценарии их взаимодействия.
- **`types/`**: Директория для TypeScript типов и интерфейсов. **Обязательно** выносите пропсы компонентов в файл `types.ts` (требование лида проекта). Это обеспечивает переиспользуемость типов и чистоту кода компонентов.
- **`hooks/`**: Вспомогательные хуки или функции, которые служат для связи UI с моделью (например, с помощью `useUnit`, `handel`).

### Композиция и сценарии

Компоненты `features` и `entities` должны быть полностью изолированными и содержать только свою собственную, атомарную бизнес-логику.

Более сложные сценарии и интеграция нескольких компонентов в единый пользовательский флоу реализуются на более высоких уровнях:

- **На уровне `widgets`**: Если несколько фич или сущностей тесно связаны и образуют единый блок (например, таблицы и кнопки по взаимодействию с данными таблицы).
- **На уровне `pages`**: Для оркестрации виджетов и фич в рамках целой страницы.

## 3. Взаимодействие с API

Все коммуникации с бэкендом (локальным Java-сервером) инкапсулированы и строго регламентированы. Прямые вызовы API из UI-компонентов запрещены.

### Паттерн вызова API

Цепочка вызовов всегда выглядит следующим образом:

**UI-компонент** -> **Модель Effector (Effect)** -> **Сервис API** -> **Сгенерированный OpenAPI клиент**

1.  **UI-компонент**: Инициирует действие пользователя (например, нажатие кнопки). Он вызывает `event` или `effect` из модели Effector (`src/models/`).
2.  **Модель Effector**: `Effect` обрабатывает асинхронную логику. Внутри него вызывается статический метод соответствующего **сервиса API**.
3.  **Сервис API (`src/shared/api/services/`)**: Этот сервис является оберткой над сгенерированным клиентом. Он подготавливает данные и вызывает нужный метод API из сгенерированного клиента.
4.  **OpenAPI клиент (`src/shared/openapi/`)**: Автоматически сгенерированный `openapi-generator-cli` клиент, который непосредственно выполняет HTTP-запрос к Java-серверу.

Этот подход гарантирует, что вся бизнес-логика и работа с API изолированы в моделях Effector, а UI-компоненты остаются «глупыми» и лишь отображают состояние.

## 4. Тестирование

Тестирование — ключевой элемент обеспечения стабильности и надежности приложения. Все новые функции и исправления должны, по возможности, сопровождаться тестами.

### Юнит-тесты

- **Инструменты:** Мы используем **Jest** и **React Testing Library**.
- **Расположение:** Юнит-тесты должны находиться в директории `__tests__` рядом с тестируемым компонентом или моделью. Например, тесты для `MyComponent.tsx` будут лежать в `__tests__/MyComponent.test.tsx`. Такое соседство упрощает их поиск и поддержку.
- **Команда для запуска:**
  ```bash
  yarn test
  ```

### End-to-End (E2E) тесты

- **Инструмент:** Мы используем **Playwright**.
- **Расположение:** Все E2E-тесты находятся в директории `test/specs/`.
- **Назначение:** Эти тесты эмулируют действия реального пользователя в собранном приложении, проверяя сквозные сценарии (например, "создать репозиторий -> добавить файл -> сохранить").
- **Команда для запуска:**
  ```bash
  yarn test:e2e
  ```

## 5. Управление зависимостями

### Фиксация версий (Pinning)

Для обеспечения стабильности и предсказуемости сборок, в проекте принято соглашение об использовании **точных версий** зависимостей (без префикса `^`). Это предотвращает автоматическое обновление пакетов на минорные и патч-версии, которое может привести к неожиданным ошибкам.

Конфигурация `yarn` (`.yarnrc.yml`) настроена так, что команда `yarn add` автоматически добавляет пакеты с точной версией.

### `dependencies` vs `devDependencies`

- **`dependencies`**: Зависимости, необходимые для работы приложения в `production`. Сюда входят фреймворки и библиотеки, используемые в клиентском коде (например, `react`, `antd`).
- **`devDependencies`**: Зависимости, необходимые только для разработки, сборки и тестирования. Сюда входят `typescript`, `eslint`, `jest`, пакеты с типами (`@types/...`) и т.д.

При установке новых пакетов используйте флаг `-D` (`yarn add -D <package>`) для зависимостей разработки.
